【问题二修复】Hero区域大标题 "CHARLES" 拼贴效果死板
----------------------------------------

问题描述：
标题字母字体完全一样，缺乏混搭感；黑底白字显示异常；字母排列过于整齐，
像网格卡片；带有不必要的统一细边框，整体缺乏"报纸剪纸"的手工破坏感。

修复逻辑：

1. 彻底混搭字体系统
   - 奇数字母（C、A、L、S）：强制使用 Impact / Arial Black 粗犷无衬线黑体
   - 偶数字母（H、R、E）：强制使用 Playfair Display 优雅衬线体，font-weight: 900
   - 之前字体分配不够极端，现在形成鲜明的视觉对比

2. 修正色彩对比方案
   - 样式A（奇数字母 C、A、L、S）：
     background: #E6E3D3（奶油白）
     color: #262320（暖黑）
   
   - 样式B（偶数字母 H、R、E）：
     background: #262320（暖黑）
     color: #E6E3D3（奶油白）
   
   - 移除了纯白背景（#FFFFFF），统一使用网站色彩系统
   - 黑底上的奶油白文字显示清晰，对比度适中

3. 移除统一边框
   - 之前：.letter 上有 border: var(--border-thick)
   - 现在：完全移除统一边框样式
   - 每个字母现在只依靠背景色和字体混搭来区分，更像真实的剪纸

4. 强化手工破坏感与不规则重叠
   
   a) 不均匀的内边距：
      - 每个字母的 padding 完全不规则
      - 例如：letter-1 为 5px 18px 12px 10px（上右下左各不相同）
      - 模拟手工剪裁时无法精确控制的边缘
   
   b) 夸张的负外边距：
      - 之前：margin: 0 -5px（轻微重叠）
      - 现在：margin-left: -12px 到 -16px（强重叠）
      - 字母之间产生明显的视觉遮挡，像堆叠的报纸碎片
   
   c) 加大的旋转角度：
      - 之前：-4deg 到 4deg 范围
      - 现在：-6deg 到 6deg 范围
      - 每个字母旋转角度随机分配，不再对称
      - 例如：C(-5deg), H(3deg), A(-2deg), R(6deg), L(-6deg), E(2deg), S(-3deg)
   
   d) Z-index 层级管理：
      - 为每个字母设置不同的 z-index（7到1递减）
      - 确保重叠时有明确的前后关系
      - 视觉上形成深度感和立体感

5. 响应式优化
   - 平板端：保持重叠效果，缩小 padding 和 margin
   - 移动端：进一步缩小字母间距，但保持混搭和不规则感
   - 确保在任何屏幕尺寸下都有"手工拼贴"的视觉冲击力

【问题三修复】主标题字母 Hover 状态层级跳跃与动画失效
----------------------------------------

问题描述：
主标题 "CHARLES" 的字母在鼠标悬停时存在两个严重问题：
1. 层级跳跃：悬停时字母会突然跳到最前面，破坏原有的前后关系
2. 动画失效：鼠标悬停时没有任何动画效果，transition 完全不工作

根本原因：
CSS 动画使用了 animation-fill-mode: both，这会强制锁定动画的最终状态。
在这种状态下，transform 属性被动画完全控制，导致：
- transition 无法介入和覆盖 transform 值
- :hover 状态的 transform 被忽略
- 交互效果完全失效

修复逻辑：

1. 移除 z-index 跳跃
   - 之前：.letter:hover { z-index: 10; }
   - 现在：完全移除悬停时的 z-index 修改
   - 效果：每个字母在 Hover 时保持原有的层级关系（C > H > A > R > L > E > S）

2. 修改 animation-fill-mode 属性
   - 之前：animation: chaotic-drop 0.9s cubic-bezier(...) both;
   - 现在：animation: chaotic-drop 0.9s cubic-bezier(...) forwards;
   - 技术原理：
     * both = forwards + backwards（强制锁定初始和最终状态）
     * forwards = 仅保持最终状态（允许后续样式覆盖）
     * 使用 forwards 后，transform 值可以被 transition 和 :hover 覆盖

3. 添加丝滑过渡效果
   - 为 .letter 基础样式添加双属性过渡：
     transition: transform 0.4s cubic-bezier(0.25, 1, 0.5, 1),
                 box-shadow 0.4s cubic-bezier(0.25, 1, 0.5, 1);
   - 技术要点：
     * 同时为 transform 和 box-shadow 添加过渡
     * 使用自定义缓动曲线 cubic-bezier(0.25, 1, 0.5, 1)
     * 缓动特性：慢启动 → 快速中段 → 柔和结束
     * 悬停进入和离开都极度丝滑

4. 优化 Hover 浮动效果
   - 之前：transform: translateY(-8px);（生硬上浮）
   - 现在：transform: translateY(-6px) scale(1.05) rotate(var(--rot));
   - 技术细节：
     * translateY(-6px)：轻微上浮，更自然
     * scale(1.05)：轻微放大，增强反馈感
     * rotate(var(--rot))：必须保留原有的倾斜角度，避免视觉错乱
     * box-shadow: 10px 10px 0px var(--dark-frame)：阴影拉长，模拟真实物理光线

技术总结：

CSS 动画优先级层级：
1. animation-fill-mode: both > 所有其他样式
2. animation-fill-mode: forwards > 允许后续样式覆盖
3. transition > 可以介入动画完成后的状态
4. :hover > 可以修改 transition 正在监听的属性

最佳实践：
- 需要后续交互的动画使用 forwards
- 纯展示型动画且不需要交互时可使用 both
- 始终测试动画完成后的交互是否正常
- transition 必须监听所有需要变化的属性（transform, box-shadow 等）

视觉效果对比：

修复前（动画失效）：
静态 → Hover → 静态
  ↓      ↓      ↓
层级1 → 层级10 → 层级1  (跳跃)
无动画 → 无动画          (失效)

修复后（丝滑流畅）：
静态 → Hover → 静态
  ↓      ↓      ↓
层级1 → 层级1 → 层级1   (稳定)
丝滑过渡进 → 丝滑过渡退  (流畅)
角度保持 → 角度保持     (完美)

【重构】语言机制：从「并排展示」改为「自由切换」
----------------------------------------

旧机制的问题：
- 只有主页有切换按钮，四个分区页与文章页完全没有入口
- data-zh / data-en 并排写死在同一元素上，动态渲染的内容
  （科目文案 / 作业卡片 / 文章正文 / 互动区）完全不受切换控制
- 按钮上「EN / 繁」把两种语言并排放在一处，并非真正的切换

新机制（i18n.js 语言引擎）：
- 单一语言状态源：localStorage（键 cp:lang），跨页面记住选择
- 文案集中注册：静态 HTML 用 data-i18n="key" 声明；
  界面文案在 shared.js 用 addAll() 注册；
  内容双语在 content.js 每条记录写 { en: '...', zh: '...' }
- 切换即时生效，无需刷新页面：
  <html lang> / 页面标题 / 导航 / 页脚 / 正文 / 表单占位符 /
  日期格式（SEP 04, 2026 ↔ 2026 年 09 月 04 日）全部同步
- 内容注册表技术字段（id / no / date / 图片路径）保持单字符串，
  只有面向读者的文字才需要双语，写起来不啰嗦

第九階段補丁 2：手機端三處顯示問題修復
================================================================

【問題一】手機端導航欄部分被遮擋
原因：.navbar 為 position:fixed 且 height 寫死 var(--navbar-height)，
      手機瀏覽器（含 iOS 瀏海屏 / 微信內建瀏覽器）頂部有系統狀態欄與
      安全區，固定定位的導航會鑽到狀態欄底下被遮住一半。
修法：全站導航引入 CSS 安全區變數 env(safe-area-inset-top)
- styles.css（主頁 .navbar / .content-area）
- shared.css（子頁 .navbar / .content-area / 600px 窄屏斷點）
  · height: calc(var(--navbar-height) + env(safe-area-inset-top, 0px))
  · padding-top: calc(原值 + env(safe-area-inset-top, 0px))
  · .content-area padding-top 同步加上安全區，避免內容被新高度壓住

【問題二】手機端 CHARLES 大字初始被裁切 + 四方格與虛線重疊
原因（兩者同源）：hero 區用固定 height（桌面 70vh / 平板 60vh / 手機 50vh），
      而字母掉落入場動畫 @keyframes chaotic-drop 的 0% 影格是
      translateY(-80px) scale(1.4) —— 需要向上溢出 80px，
      固定高度 + 預設 overflow 會把初始影格裁掉；
      同時手機端 hero 高度不足以容納「標題 + 副標 + 四個方格」，
      內容溢出壓到下方的剪刀虛線。
修法：
1. hero 高度由固定 height 改為 min-height（三處斷點全改）：
   桌面 70vh / 平板 60vh / 手機 calc(50vh + 40px)
   → 內容偏高時自動撐開，不再裁切、不再壓線
2. 三處 hero 皆加 overflow: visible，允許動畫初始影格向上溢出不裁切
3. 手機端 hero padding 改 24px 8vw（上下留白），
   並加 .hero-section { margin-bottom: 24px } + .scissor-divider { margin-top: 8px }
   → 明確保證方格與虛線之間有間距
4. 手機端另加大 .subject-buttons margin-top 40 → 32px 收緊節奏

※ 中途試過「手機 hero 改 height:auto」的方案，實測發現 600px 斷點的
  min-height 反而把方格推出首屏，已回退改用 min-height 方案（最終版）。

【問題三】子頁面剪刀圖標樣式與主頁不一致（主頁正常）
原因：主頁的剪刀是內聯 SVG（線稿），

      → 在不同系統/瀏覽器下被渲染成彩色 emoji（紅把銀刃），與主頁不符。
修法：
1. 四個科目頁把 emoji 全部換成主頁同款內聯 SVG（24×24 viewBox 線稿剪刀）
2. shared.css 的 .scissor-divider .scissor-icon 補上尺寸約束：

   → 這條同時修掉一個潛在事故：SVG 未限尺寸會被 flex 拉伸成 318px 高

【二】全站程式碼體檢

■ 性能修復 4 處

1) shared.js ── 修掉真正的監聽器洩漏（本次體檢最大收穫）

第十三階段補丁二：中文版雙欄的兩個渲染缺陷修復
================================================================

更新日期：2026年9月23日
對應交付：article.css（article.html 全模版生效）

【問題】

一、中文版第 1 欄末尾出現一個小奶油白塊（英文版沒有）。
二、引用塊的引號壓住了正文首行（「零實務經驗……」被蓋住）。

【診斷】

· 白塊 = 引用塊的 ::before 引號盒。舊實現是 position: absolute
  （top: -20px 釘在框上）。雙欄分欄平衡時，Chrome 先把引用塊在
  第 1 欄底部排版、再因 break-inside: avoid 整體搬到第 2 欄，
  但絕對定位盒的繪製位置沒有隨之失效 —— 引號盒被遺留在第 1 欄
  底部，成為孤立的奶油白塊。中英文內容長度不同、分欄平衡點不同，
  中文必現、英文剛好躲過。
· 引號遮擋：引號盒高 68px、下緣伸入框內 ≈48px，正文首行卻從
  框頂 +29px 開始。拉丁字形位置低勉強躲過；CJK 字形撐滿整個
  em 框、位置更高，首行左端被奶油白底襯蓋住。

【修法（根治：引號改為文檔流內元素）】

· ::before 棄用 position: absolute，改為 display: block +
  width: fit-content + margin: -22px 0 8px 20px —— 負 margin
  上移釘住上邊框，「釘住」觀感不變；文檔流內元素隨盒子整體
  重繪，分欄搬運時不可能被孤立。
· blockquote 頂部內邊距 26px → 0（引號佔據流內第一行，
  正文自然落在引號盒下方，首行頂部 +41，距引號盒下緣 +32
  有 9px 淨空，中英文皆不受遮擋）。
· blockquote 加 display: flow-root（獨立格式化上下文，
  配合流內引號確保分欄時整塊搬運、內部不產生碎片）。

【驗證】

· .workbuddy/verify-quote-fix.mjs（網格 elementsFromPoint 掃描
  第 1 欄末尾區域）：修復前 ZH 30 處 / EN 24 處命中 BLOCKQUOTE
  （= 白塊洩漏），修復後 ZH / EN 均為 0。
· 視覺核對 ZH / EN 1920 截圖：白塊消失、引號文字完整、
  釘住觀感不變。
· 回歸：domtest 189（引號護欄改為斷言「流內負 margin 實現 +
  禁用絕對定位」）/ verify-bcm241-a1 101 / uishot 22 → 0 失敗。

【經驗教訓（勿回退）】

雙欄容器（multicol）內禁止對 ::before/::after 使用絕對定位 ——
break-inside: avoid 觸發的整欄搬運會遺留 stale 繪製。
凡要「越出盒子邊緣」的裝飾（引號釘、膠帶），用流內負 margin 實現。

· 對齊這件事要「量文字，不要量盒子」。
  方框左緣 ≠ 文字左緣：padding-left / text-indent / border-left
  都會讓方框與文字錯開。要驗證對齊，必須用 Range 取首行文字的

· 懸掛縮進（padding-left + 負 text-indent）本身是對的學術規範，

  一旦選定，就要讓所有層統一，不能各用各的 padding。
· 「東西退到盒子外面」優先用流內負 margin，不要用絕對定位。
  這條在 multicol 環境裡尤其硬性——multicol 觸發整欄搬運時，
  絕對定位的盒子會被遺留在原位變成白塊（本專案第十三階段踩過）；
  負 margin 則跟著流一起搬，安全。
· 結構對齊類的修訂最好留一個「腳本化守衛」。
  純眼睛看容易漏（尤其是只有 3px、0.5px 的偏差），
  寫成 _refalign.mjs 這種可重複執行、逐尺寸斷言的量測腳本，
  以後改 padding 會立刻被抓出來。

【用戶需求】

兩件事：① 加載動畫；② 代碼結構優化。加載動畫是治標，得先弄清楚
「卡」的病根在哪 —— 查下來發現真因不在代碼，在圖片。

【一、病根：全站圖片 23 MB，單張封面 1.8 MB】

· assets/posts 16 MB、assets/subjects 6.1 MB、slides 1.4 MB，
  合計 23.3 MB。
· 像素其實不大（1024×683、1216×790），但全是**未壓縮 PNG**：
  單張 1.2～1.8 MB。一張封面頂得上半本雜誌，翻頁當然會頓。
· 結論：先修這個，動畫才有意義 —— 否則動畫只是把「慢」藏起來。

【二、治本：批量轉 WebP（省 86%）】

· 全站 20 張圖轉出同名 .webp，原 PNG **全部保留在位**（不覆蓋存檔）：
    23.27 MB → 3.32 MB（省 86%）
    封面 bcm206-a1-cover：1272 KB → 143 KB
    科目 hero bcm241-hero：1598 KB → 149 KB
    人像 charles-portrait：40 KB → 5 KB
· 質量取捨：先跑了 PSNR 客觀量測（q78/q82/q85/q88 四檔），
  這些圖帶紙張噪點肌理（高頻細節多，有損壓縮損失偏大），
  最終定 q=85（PSNR 31～36 dB）；簡報逐頁圖要能全屏放大讀字，
  單獨提到 q=90。
· 接入方式：**不改 content.js 一個字**。新增 shared.js 的
  `ZineUtil.imgSrc()`，把 .png/.jpg 路徑統一改寫成 .webp；
  靜態 HTML 裡寫死的圖（首頁人像）由 `upgradeStaticImages()`
  掃一遍補上；燈箱動態改 src 的圖也自動生效（src 取自 slide，
  已是 webp）。

· **WebP 兜底**（`bindImageFallback()`）：用捕獲階段監聽 error
  （error 事件不冒泡，只能在捕獲階段撈到），圖片加載失敗且路徑
  以 .webp 結尾時退回同名原圖，並用 `data-fallbackTried` 標記
  防止死循環。一處覆蓋全站，不用給每張圖掛 onerror。
  → 原 PNG 留著不只是「存檔」，它是這條兜底鏈的後半段。

【三、治標：翻頁加載動畫（洗牌翻頁）】

· 視覺沿用站點語言：松石青底 + 三張奶油白紙卡（3px 深色邊 +
  4px 硬陰影）依次翻面，下方 Varela Round 的 LOADING／載入中
  寬字距標籤。z-index 9998 —— 壓在紙張噪點(9999)之下，
  肌理照樣蓋在它上面，不像一塊外來白屏。

· 三個時間閘門（這才是「不煩人」的關鍵）：
    ① **180ms 才亮起** —— 緩存命中、秒開的頁面根本看不到它，
       不為快頁面憑空加一閃而過的白屏；
    ② **無人接管 300ms 收掉** —— 首頁沒有首屏大圖，走這條；
    ③ **頁面渲染器調 waitImage() 表示「本頁要等圖」**，期限放寬
       到 1.5s，且通常由圖片的 load／error 提前觸發。
  → 這樣既不會「永遠轉」，也不會「沒圖就先收、收完圖才來」。

· 安全性：
    · 加載層**內聯在每個 HTML 的 body 開頭**（不是 JS 生成），
      才能趕上首屏第一幀，不等腳本；
    · 另有**純 CSS 的 6s 保險絲**（@keyframes loader-failsafe）：
      萬一腳本整個掛了，遮罩也會自己消失，不會把頁面永久鎖死；
    · prefers-reduced-motion 下停掉翻牌，改成緩呼吸。

· 首圖還加了 `fetchpriority="high"` + `decoding="async"`：
  提前下載、解碼不阻塞文字渲染。

【經驗教訓】

· **「卡」要先量再治**。這次一上來想的是「加個動畫蓋住」，
  但先花五分鐘量了素材體積 —— 23 MB 對 3.3 MB，
  動畫只是止痛藥，壓圖才是消炎藥。兩件都做了，但順序不能反：
  如果只做動畫，用戶會覺得「還是慢，只是多了個轉圈」。

· **加載動畫最大的風險不是醜，是煩**。秒開頁面被強行塞一個
  0.3 秒的動畫，比沒有動畫更糟。所以「延遲亮起」是必須的，
  不是加分項 —— 180ms 這個閘門比動畫本身重要。

· **有損壓縮參數別憑感覺定**。這批圖帶紙張噪點肌理（高頻細節多），
  PSNR 只有 31～36 dB —— 換成普通照片這個數值會很難看，

  再加一條自動回退 —— 這樣「優化」萬一翻車，最壞也只是回到原狀，

【診斷】
· 大屏雙欄下，Reference 區自成分欄片段：左欄排到第二組就停住，
  第三組整塊被推到右欄頂部，左欄底部空出 232px（1440）／200px（1280）。
· 真因不是間距，而是分欄平衡演算法：三組「h3 + 文獻條目」高度相同，
  每組又是 break-inside:avoid 的不可拆分塊；瀏覽器取「內容剛好裝下的
  最小欄高」，左欄裝不下第三組就整塊搬走，留下填不滿的空位。
  純調間距只在特定寬度有效（1180 以下缺口反而擴大到 250px+），治不了本。

【做法】收尾區塊獨佔右欄（article.css，一條規則）
· `.article-body > .inline-note:has(+ .embed-rule) { break-before: column }`
  —— 讓緊接影片塊的那條「生成式 AI 使用聲明」強制另起一欄。
  斷欄點被釘死後，左欄就必須裝下全部文獻：第三組回到左欄最底部，
  聲明與影片留在右欄當收尾區塊。
· 用 :has() 精確鎖定「影片塊前的那條聲明」，正文中段的聲明不受影響；
  窄屏單欄本來就沒有分欄，這條規則天然不生效。
· 空位沒有消失，只是從「左欄中段」搬到「右欄最底部」—— 也就是文章
  結束後的頁尾留白，那才是雜誌版面該有的樣子。

【走過的彎路（記下來避免重複）】
1. 讓 Reference 的 h2 通欄（column-span: all）能修好 1180-1440，
   但 1100 反而更糟（左欄空位 178 → 249）：標題離開左欄後，參與平衡的
   內容變少，演算法又找到更小的欄高。已撤。
2. 允許文獻條目跨欄拆分（break-inside: auto）能填滿左欄，但書目與
   「↗ 連結 / 註解」被拆到兩欄，右欄頂部出現孤立的連結與註解。已否決。
3. 真正的關鍵是「釘死斷欄點」，而不是「讓內容自己平衡」。

【驗證】
· 全量回歸 **706 項 0 失敗**（domtest 219→221，新增兩條護欄：
  收尾聲明斷欄規則、.embed-rule 與影片塊的相鄰結構）。
· 新增 .workbuddy/_refcolumn.mjs（真實瀏覽器；實驗用的 _refgap/_refspan

  × 中英雙語，驗標題位置、第三組落在左欄、左欄空位 ≤ 8px、左欄收尾是
  最後一條文獻、無橫向溢出；另跑 1000 單欄檔確認斷欄規則不誤觸。

【經驗教訓】
· **multicol 的「空位」是平衡演算法的產物，不是間距問題**。一欄裡排幾個
  等高的不可拆分塊時，欄底必然留下「裝不下下一個塊」的缺口；改間距只能
  碰運氣地在某些寬度生效，換個寬度缺口又回來。可靠解法只有兩條：
  ① 讓內容以更細的粒度拆分（犧牲條目完整性）；② 用 break-before: column
  把斷欄點釘死，讓某一欄的內容成為定數。
· **空位不會消失，只會搬家**。填滿左欄的代價是右欄底部多出留白 ——
  但那段留白落在文章末尾，讀起來是頁尾呼吸空間，而不是版面中段的破洞。
· **沙箱會攔下 >50 個檔案的批量刪除**（Chrome profile 有幾百個檔案）：
  量測腳本的 profile 目錄改用時間戳命名、不做刪除，天然避開。

第二十四階段（續）· 表格分隔線修復（使用者回饋）
────────────────────────────────────────────────────────

【問題】實驗變項表「分隔不清晰」—— 變項組與常數（控制變項）組之間看不出分界。

【真因（兩個疊在一起）】
· 組間線原本只掛在分組軸那一格上，而那格只佔 22% 寬 —— 右邊 78% 寬仍是
  一條與組內行間等粗等淡的虛線，整張表讀起來是一坨。
· **更關鍵：那條線從頭到尾就沒畫出來過。** `--border-medium` 本身是完整
  簡寫（`2px solid #262320`），寫成 `border-top: var(--border-medium) solid
  var(--dark-frame)` 會展開為 `2px solid #262320 solid #262320` —— 非法值，
  整條宣告被靜默丟棄。分組軸右側的豎線（border-right）是同一個寫法，
  也一直是死的。瀏覽器不報錯、CSS 文本看著完全正常，只有 computed 值
  露出馬腳：`0px none`。

【修法】
· 全站 `var(--border-thick/medium) + solid/顏色` 的拼寫一律改為直接引用

· 組間線改畫在**組首行的三格**上（`> *`）：三格各帶 2px 實線，collapse 下
  合併成一條橫貫三列的線。渲染器給每組首行打 `.tbl-group-start` 標記；
  第一組用 `:not(:first-child)` 排除（緊貼表頭墨條，再加線會成雙線）。
· 分組軸底色 0.22 → 0.30，軸右側豎線復活，「標籤帶 / 內容區」一眼分欄。
· 窄屏堆疊態用同特異性覆寫：把格上的線清掉、改畫在整張卡片（`<tr>`）上，
  組首行再向上多留 18px，靠留白 + 實線雙重斷組。

【三級分隔層級（定稿）】
  表頭墨條（3px 粗邊）＞ 組與組之間（2px 實線，橫貫三列）＞ 組內相鄰行（1px 虛線）

【經驗教訓】
· **先確認 CSS 令牌是不是「完整簡寫」**：`--border-thick: 3px solid #262320`
  用在 `border:` / `border-top:` 時必須**單獨引用**；再拼 `solid #xxx` 就是
  非法值、整條宣告作廢。這類 bug 完全靜默、無任何報錯，讀 CSS 文本看不出
  來 —— 只有量 computed 值（或看渲染結果）才抓得到。
· **靜態 CSS 斷言有盲區**：它只能證明「寫法符合約定」，證明不了「瀏覽器
  接受了這個值」。凡是靠自訂屬性拼出來的分隔線 / 邊框 / 陰影，都要在真機
  量測腳本裡補一條 computed 值斷言。
· 像素掃描找分隔線，判據要用「**橫向最長連續暗段**」而不是「暗像素佔比」：
  文字成簇、虛線短段、實線長段三者能一次分開；佔比法會把大片色底誤判成
  暗區（本站松石青底灰階 149，低於常用閾值 165）。
